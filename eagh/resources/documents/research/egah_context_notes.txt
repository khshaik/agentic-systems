Evidence-Governed Agent Harnesses: Making Evidence Survive Long-Running Agent Execution
Abstract

Long-running AI agents introduce a production problem that is easy to overlook: preserving execution state is not necessarily the same as preserving the evidence that justified the execution.

An agent may plan a multi-step workflow, invoke tools, retrieve information, make intermediate decisions, and eventually reach a consequential action many steps later. If the workflow crashes at step 40 of 60, conventional checkpointing can restore execution state, but the harness may still lack a durable representation of what was verified, what was accomplished, which evidence remains valid, and what should be revalidated before execution continues.

This talk presents Evidence-Governed Agent Harnesses (EGAH), an engineering approach that treats evidence as a first-class runtime object alongside graph state, checkpoints, memory and tool execution. The approach introduces evidence checkpoints, evidence envelopes, verification history, outcome attribution and capability boundaries directly into the agent execution graph rather than treating governance and auditability as external layers.

The core execution pattern evolves from:

Plan → Tool Call → Result → Next Step

to:

Plan → Evidence Checkpoint → Tool Call → Result Verification → Evidence Update → Next Step

This provides a practical mechanism for determining whether an agent should continue execution, refresh evidence, request human intervention, or escalate to a more capable model.

The approach also provides a way to think about the growing use of small models in production. Instead of asking whether a tuned 8B model is simply "good enough" in general, the harness can establish evidence-backed capability boundaries for specific task classes. Tasks within an established boundary can use a smaller, cheaper model; boundary-near tasks can trigger verification or human review; tasks beyond the boundary can escalate to a larger model.

The talk will examine the architecture, execution model, evidence-state design, crash-recovery implications, small-model capability boundaries, resource/outcome accounting, and the trade-offs introduced by additional verification. It will also distinguish between what is currently demonstrated by the design and what remains to be validated through implementation and production experimentation.

The central proposition is:

A production agent harness should persist not only where the agent was, but also what the agent knew, what it verified, what it accomplished, and what it is still authorized to do.

Problem

Agent engineering has progressed rapidly from prompts to context, harnesses, loops and graphs. In production, however, another dimension becomes increasingly important: evidence state.

A conventional long-running agent can be represented as:

Plan → Tool → Result → State Update → Next Step

The harness may persist:

graph state,
conversation/context state,
tool results,
checkpoints,
memory,
execution metadata.

But consequential workflows introduce additional questions:

Was the information used to make a decision still valid?
Which prerequisites were actually verified?
When were they verified?
What changed after verification?
Which actions were already completed?
Which outcomes were independently confirmed?
What authorization existed at the point of execution?
If the workflow resumes after a crash, should the agent simply continue from the checkpoint?
Should some evidence be revalidated before allowing the next action?

These questions become particularly important as agents operate for longer periods, use more tools, interact with changing external systems and make decisions across multiple execution steps.

The CFP's example of an agent crashing at step 40 of 60 therefore exposes a broader production concern:

Checkpoint recovery can restore computational state without necessarily restoring the evidentiary context required to safely continue the workflow.

EGAH explores treating that evidentiary context as part of the runtime state itself. The attached research document identifies this distinction explicitly as "State vs Evidence" and proposes preserving evidence state alongside execution state.

The intention is not to validate every operation indiscriminately. Rather, verification becomes an explicit part of the harness's execution semantics, particularly around actions where evidence, authorization, model capability or external state materially affect the decision.

The proposed evidence state extends conventional agent state with structured information about what has been observed, verified and accomplished.

An evidence envelope can capture information such as:

execution phase,

verification status,

The supplied document defines an evidence-envelope schema containing these concepts and associates resource consumption and outcome attribution with the evidence record.

This enables the harness to distinguish between:

That distinction becomes increasingly important in long-running agent workflows.

What I Would Share With Practitioners

The talk would focus on the practical lessons rather than presenting EGAH as a finished product.

Lesson 1 — State is not the same as evidence

Persisting graph state does not automatically preserve why a decision was made.

Lesson 2 — Evidence needs lifecycle semantics

An evidence object should have provenance, timing, verification status and applicability rather than being treated as an immutable fact.

Lesson 3 — Verification belongs near consequential boundaries

Not every token, tool call or intermediate step requires the same level of validation.

Lesson 4 — Small models need capability boundaries

The practical question is not whether a small model wins against a frontier model globally, but where it is sufficiently reliable for a defined class of tasks.

Lesson 5 — Recovery needs semantic continuity

After a crash, resuming execution should consider whether the evidence supporting the next action is still valid.

Lesson 6 — Governance should earn its place in the harness

Every additional checkpoint has a cost. Verification should therefore be measurable and tied to an actual reliability, safety or decision-quality requirement.

Lesson 7 — Measure before declaring production readiness

Checkpoint overhead, recovery correctness, boundary accuracy and outcome quality should be measured before additional harness complexity becomes permanent infrastructure.

Yes — and this is a very important challenge to address before submitting the paper/talk.

The short answer is:

EGAH is not fundamentally an observability framework. It can—and should—use existing observability frameworks such as OpenTelemetry, Langfuse, Phoenix, Datadog, etc. as its telemetry/monitoring layer.

The research distinction is that observability tells you what happened; EGAH uses durable, verified evidence to determine what the agent is allowed to do next.

That distinction should become explicit in your paper and presentation.

1. What existing observability already does

Modern AI observability has become quite sophisticated.

For example, OpenTelemetry's GenAI conventions can capture model calls, token usage, latency, tool calls and, when enabled, prompts, completions, tool arguments and results.

Likewise, Langfuse can trace:

LLM generations

and can attach evaluations to individual operations.

So if EGAH merely says:

"Let's log evidence, tool calls, tokens, verification and outcomes."

then it is not sufficiently novel.

That would largely be an observability/telemetry implementation.

EGAH asks:

That's a different problem.

"What happened?"    "What can happen next?"
